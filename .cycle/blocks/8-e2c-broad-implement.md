ST3 (E2c) | teller/services/txn-watermark.js | new: readMark(db) → { id: MAX(transactions.id) (0 when empty), at: now() } as text, read before the candidates; windowSql({ alias, watermark, since, mark, overlapHours = 24 }) → the WHERE fragment (id <= mark AND (id > watermark OR created_at > since − overlap)) + inOverlap (id <= watermark); advanceSql(idCol, atCol) → GREATEST on both (never backwards). REGRESSION RISKS: (1) A transaction left open longer than 24 h before a check commits rows the overlap no longer reaches (the created_at mark waited for it instead — it never lost a row, it held every later alert back). (2) The anomaly candidate query adds a NOT EXISTS over notification_log per surviving candidate (few rows after the 7-day / 3× filters; no index on data->>'transaction_id'). (3) An anomaly push whose notification_log row didn't land now holds the watermark (it used to advance) — the next sync retries it; the pushes that did land are skipped by the dedupe. (4) "Paycheck landed" now writes its watermark on a run that found nothing (it skipped the write). (5) In a deploy overlap the old code advances only the time watermarks; the new code then re-reads from its stored id, and the dedupe keeps an already-announced row from repeating.
